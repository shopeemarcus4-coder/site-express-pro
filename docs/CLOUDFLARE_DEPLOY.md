# Preparar publicação externa com Cloudflare D1

O repositório sincroniza código com a Lovable, mas essa sincronização não cria um banco de dados. O build atual da Lovable usa Cloudflare Workers e não tem o binding `SITE_EXPRESS_DB`; cadastro e salvamento precisam dele. O backend integrado da Lovable consome _Run credits_ segundo a [documentação da Lovable](https://docs.lovable.dev/features/cloud), então este procedimento usa uma conta Cloudflare separada. Ele não aciona a IA da Lovable.

Este preparo não publica nada. A conta Cloudflare, o banco D1 e a decisão de publicar ficam com o responsável pelo projeto. Confira as cotas e condições atuais do plano da sua conta antes de usar um serviço externo; este repositório não presume nem contrata um plano pago.

1. Na sua conta Cloudflare, crie um banco **D1** e anote o **nome** e o **Database ID** reais. Não coloque tokens ou senhas no repositório. O Database ID é um UUID; sem ele, o script se recusa a gerar a configuração.
2. Gere o Worker localmente com `npm run build`. O build deve produzir `.output/server/wrangler.json`, `.output/server/index.mjs` e `.output/public/`.
3. Na mesma sessão do terminal, defina `SITE_EXPRESS_D1_DATABASE_NAME` e `SITE_EXPRESS_D1_DATABASE_ID` com os valores reais da sua conta. Depois execute `node scripts/prepare-cloudflare-deploy.mjs`.
4. Revise `.output/server/wrangler.site-express.json`. Ele mantém a configuração gerada pelo Nitro e adiciona `d1_databases` com `binding: SITE_EXPRESS_DB`. Fixa a data de compatibilidade em `2026-05-27`, testada no Wrangler local; a data gerada pelo Nitro (`2026-10-23`) excedeu a data máxima reconhecida pela versão local de `workerd`. O arquivo fica em `.output/`, que é ignorado pelo Git. O script não o sobrescreve se já tiver conteúdo diferente; revise ou remova o arquivo gerado antes de repetir com outro banco ou build.
5. Quando houver autorização para publicar, instale o CLI **Wrangler** somente neste projeto, a partir do [pacote oficial da Cloudflare](https://github.com/cloudflare/workers-sdk/tree/main/packages/wrangler), faça login na sua conta e use o arquivo preparado: `./node_modules/.bin/wrangler deploy --config .output/server/wrangler.site-express.json`. Não execute o deploy sem revisar nome do Worker, binding, conta e ambiente. A versão 4.152.0 do pacote oficial foi conferida no registro npm (licença MIT ou Apache-2.0, Node >=22); este projeto ainda não a instalou.
6. No endereço publicado, teste de verdade: cadastrar uma conta de teste, confirmar `GET /api/auth/session`, criar e salvar um site, recarregar a página, abrir o site público e sair. Repita o teste após reiniciar ou atualizar o Worker para confirmar a persistência. Remova a conta de teste quando houver uma rotina administrativa apropriada; ainda não há exclusão de conta na interface.

O adaptador usa `request.runtime.cloudflare.env.SITE_EXPRESS_DB`, conforme o guia Cloudflare incluído no pacote Nitro instalado. A configuração D1 gerada aqui serve para um Worker publicado **na sua conta Cloudflare**. Não há evidência de que a publicação gerenciada pela Lovable aceite esse binding personalizado. Publicar apenas pela Lovable sem configurar um banco compatível mantém a interface visível, mas não torna cadastro e dados persistentes operacionais.

Para executar sem Cloudflare, o servidor Node usa SQLite. Nesse caso, faça um build Node fora do ambiente da Lovable e defina `SITE_EXPRESS_DB_PATH` para um volume persistente. O padrão `/tmp/site-express-pro.sqlite` é adequado somente para desenvolvimento local.
